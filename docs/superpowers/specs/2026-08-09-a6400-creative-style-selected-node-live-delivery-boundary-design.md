# α6400 Creative Style Selected-Node Live Delivery Boundary Design

## Status and scope

This design continues the approved static/offline α6400 research program from
commit `f57b2fce26a867280a455efff9469f297caa94ef`. It deepens the checked
selected-node identity artifact at its current first unresolved boundary:

`viewsettingmenu-live-selected-ordinals-1-5-2-and-productaction-10-delivery`

Creative Style remains target-native substrate only. This work must not promote
it to first-class Creative Look, infer image-processing semantics, authorize
installation, relax recovery gates, or make camera testing eligible.

## Objective

Upgrade `analysis/a6400-creative-style-selected-node-identity-boundary.json` to
schema 3 and answer two narrow questions from authenticated sources:

1. Which typed Caution setting-node paths write the selected-ordinal field at
   `+0x18`, and does any exact source-derived chain establish the required live
   ordinal triplet `1,5,2` for the proven Creative Style child path?
2. Does any fully decoded canonical VU2 slot-37 call deliver selector `10` on a
   receiver whose vptr identity is proven to be `ViewSettingMenu` address point
   `0x8E2270`?

A negative result is useful only when its scan universe is explicit. The design
must narrow the first opaque boundary without turning a bounded negative into a
whole-program absence claim.

## Approaches considered

### 1. Extend the selected-node artifact to schema 3 — selected

Add a selected-ordinal writer inventory and a classified ProductAction caller
inventory to the existing contract, exporter, tests, checked report, and
deep-dive text. These facts use the artifact's already pinned VU2 and
CautionConfig sources and refine its exact current boundary.

### 2. Add a standalone live-delivery report

This would isolate the two scans, but it would duplicate source identities,
ViewSettingMenu vtable facts, lifecycle semantics, negative claims, and the
`1,5,2` verdict. It would also add another report dependency without creating an
independent product or safety decision.

### 3. Fold the work into the activation-caller report

The activation report already owns selected-node property access, manager
slots, and process-data routing. Adding Caution lifecycle writers and generic
ProductAction caller classification would mix three distinct proof boundaries
and make mutation failures harder to attribute.

## Evidence architecture

### 1. Selected-ordinal writer inventory

The exporter will retain the already validated base lifecycle and selected-state
owners, then derive an exact inventory of relevant writes to receiver field
`+0x18` from authenticated `CautionConfig.so`.

Each accepted writer record must include:

- exact EXIDX or symbol owner and complete decode status;
- instruction site, width, source register, receiver register, and displacement;
- receiver provenance as `this`, resolved child, or unresolved object;
- source-value provenance, including the arithmetic or helper return that
  produces the stored value;
- role classification: recursive initialization, fallback initialization,
  selected-item cache update, or unresolved/unrelated;
- whether the writer is on a source-derived path from the typed base lifecycle
  invoked through `ViewSettingMenu`'s product-root initialization call.

The initial inventory must include the already pinned writes at `0x7C73CE`,
`0x7C7470`, and `0x7C6C00`. The exporter must discover or validate them from
decoded instructions rather than copying report constants. Any additional
matching store in the bounded typed-method universe must either be represented
and classified or fail export.

The required ordinal route is `[1,5,2]`, corresponding to the proven static
Creative Style child-index path `[0,4,1]`. A positive conditional route requires
all of the following:

- the same root/list objects already proven by the selected-node artifact;
- exact one-based index conversion for each level;
- a continuous receiver/child identity chain through all three levels;
- exact writes or cache updates that place `1`, `5`, and `2` in the three parent
  selected-ordinal fields;
- the candidate Caution lifecycle provider at every virtual boundary.

Even if all five conditions hold statically, the report must distinguish
`candidate_provider_conditional_ordinal_triplet_proven` from
`runtime_selected_ordinal_triplet_1_5_2_proven`. Runtime liveness remains false
unless dynamic binding and execution/order are independently established.

### 2. ProductAction caller classification

Retain the source-derived VU2 function-aware scan over `.ARM.exidx` owners and
the six canonical receiver-vptr → slot `+0x94` → `BLX` calls. Extend each record
with bounded provenance rather than hard-coded false fields:

- exact owner symbol/RTTI/vtable identity when available;
- receiver origin at the call, including entry argument, helper return, field
  load, or unresolved value;
- selector origin at the call, including immediate assignment, preserved entry
  argument, call-clobbered value, or unresolved value;
- any relocation-backed address-taken owner relationship;
- a reason code explaining acceptance or rejection.

A candidate is accepted only when the same receiver is proven to carry
ViewSettingMenu address point `0x8E2270` and `r1` is proven equal to decimal 10
at the slot-37 transfer. Name similarity, shared slot number, address proximity,
or a compatible base class is insufficient.

The scan remains bounded to fully decoded canonical VU2 calls. The report must
continue to expose the 1,594 incomplete/terminal owners and explicitly exclude
noncanonical virtual dispatch, indirect/runtime callbacks, cross-module loader
delivery, and unobserved execution. `whole_program_absence_proven` remains
false.

### 3. Verdict composition

The two new sections are independent. A conditional ordinal result must not
promote ProductAction delivery, and a selector-10 caller must not promote the
selected-node identity unless the exact ordinal chain is also closed.

Possible positive claims are limited to:

- a complete typed selected-ordinal writer inventory;
- a candidate-provider-conditional `1,5,2` ordinal route, if source dataflow
  supports it;
- source-derived classifications or refutations for individual canonical
  ProductAction callers;
- receiver-proven selector-10 delivery only if one exact candidate satisfies
  both acceptance predicates.

Claims that remain false unless independently proven are runtime provider
binding, runtime selected ordinals, runtime selected node equals Creative Style,
process-ID 42 activation, ViewCreativeStyle factory invocation, first-class
Creative Look, processing/output behavior, installability, recovery validation,
and camera-test eligibility.

If no exact caller or ordinal chain closes, the first unresolved boundary must
be narrowed to the earliest concrete missing writer/receiver/caller edge found
by the source-derived inventories. It must not reuse a broader stale phrase.

## Export and normalization

The existing exporter remains the sole producer. It will:

1. validate both authenticated source identities and all upstream report
   digests before analysis;
2. derive the writer and caller inventories from decoded source data;
3. exact-match the bounded expected inventory, including universe counts and
   explicit exclusions;
4. emit schema 3 only after every positive and negative contract check passes;
5. keep all source mutations in memory and never modify firmware artifacts.

The normalizer must reject unknown or missing schema-3 fields, changed inventory
records, promoted runtime/safety claims, changed readiness, stale dependencies,
and narrative drift. The checked JSON report remains deterministic.

## Testing and acceptance

Tests are written before implementation. They must reject mutations to:

- every accepted `+0x18` store's instruction class, operands, receiver, source,
  and owner;
- one-based arithmetic and each identity hop required by any conditional
  `1,5,2` route;
- discovered-writer completeness and role classifications;
- each canonical slot-37 vptr load, slot load, call register, receiver origin,
  selector origin, owner identity, and reason code;
- fully decoded/incomplete owner counts and excluded-universe wording;
- report dependencies, schema, readiness, conclusion, and every promotion
  guard.

Acceptance requires deterministic checked-report regeneration, equality with a
fresh authenticated-source export, focused selected-node and activation tests,
full analysis and safety suites, Python compilation, `git diff --check`, a clean
worktree, and synchronized local/upstream/remote commit identities. No Sony
binary, camera, updater, USB, partition, or package action is introduced.
